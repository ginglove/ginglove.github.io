Phần 1.1 — Chaining Requests Là Gì?

Chaining Requests = Lấy dữ liệu từ response của request A → lưu vào biến → dùng làm input cho request B. Tạo thành chuỗi giao dịch tự động, không cần copy-paste.

Không Có Chaining (Thủ Công)

1. Gửi POST /login → nhận token "QpwL5tke..."

2. Copy token bằng tay → paste vào Header request tiếp

3. Gửi POST /transfer → nhận transaction_id: "TXN-8821"

4. Copy transaction_id bằng tay → paste vào URL request tra cứu

Chậm, dễ sai, không chạy được Collection Runner tự động!

Có Chaining (Tự Động)

1. Gửi POST /login → Script tự lưu token vào biến

2. Request tiếp tự đọc {{token}} từ biến → gửi đi

3. Gửi POST /transfer → Script tự lưu transaction_id

4. GET /transaction/{{txn_id}} → tự động tra cứu

Nhanh, chính xác, chạy Collection Runner 1 click!

Phần 2.1 — Postman Assertions Chi Tiết

Mỗi assertion được bọc trong pm.test("tên test", callback) — Postman sẽ hiển thị PASS/FAIL riêng cho từng test này trong tab Test Results. 

pm.test("Status code là 200", () => {
    pm.response.to.have.status(200);
});

pm.test("Status code nằm trong danh sách hợp lệ", () => {
    pm.expect(pm.response.code).to.be.oneOf([200, 201]);
});
const res = pm.response.json();

pm.test("Response chứa token", () => {
    pm.expect(res).to.have.property("token");
});

pm.test("Email đúng định dạng", () => {
    pm.expect(res.data.email).to.include("@");
});
pm.test("Response time dưới 500ms", () => {
    pm.expect(pm.response.responseTime).to.be.below(500);
});
pm.test("Content-Type là application/json", () => {
    pm.response.to.have.header("Content-Type");
    pm.expect(pm.response.headers.get("Content-Type")).to.include("application/json");
});

Phần 2.2 — Viết Assertions Thực Chiến (Có Giải Thích)

Ví dụ thực tế trên Restful-Booker: mỗi tab là một nhóm assertions — code bên trái, giải thích TẠI SAO bên phải.

Code — POST /auth: 
// Kiểm tra API có trả thành công?
pm.test("Auth trả về status 200", () => {
    pm.response.to.have.status(200);
});

// Kiểm tra API không trả 201 hay 204
pm.test("Status chính xác là 200", () => {
    pm.expect(pm.response.code).to.eql(200);
});

// Kiểm tra performance
pm.test("Response time < 2 giây", () => {
    pm.expect(pm.response.responseTime)
        .to.be.below(2000);
});

.to.have.status(200)

So sánh status code chính xác. Nếu server trả 400/401/500 → test FAIL ngay, giúp phát hiện lỗi sớm.

.to.eql(200) vs .to.have.status(200)

Cùng kiểm tra 200, nhưng eql so sánh giá trị number còn have.status là cú pháp chuyên dụng cho HTTP.

Tại sao test time?

Login mất > 2s = user bỏ app. Performance cũng là bug! Dùng .to.be.below(ms) để set ngưỡng.

Code — Kiểm tra response body: 
const res = pm.response.json();

// Field có tồn tại?
pm.test("Response có field token", () => {
    pm.expect(res)
        .to.have.property("token");
});

// Kiểu dữ liệu đúng?
pm.test("Token là string", () => {
    pm.expect(res.token).to.be.a("string");
});

// Giá trị không rỗng?
pm.test("Token không rỗng", () => {
    pm.expect(res.token.length)
        .to.be.above(0);
});

// Giá trị chính xác?
pm.test("Không có field reason", () => {
    pm.expect(res)
        .to.not.have.property("reason");
});

.have.property("token")

Backend quên trả token → test FAIL ngay. Luôn kiểm tra field tồn tại trước khi kiểm tra giá trị.

.to.be.a("string")

Token phải là string, không phải null, number hay boolean. Sai kiểu = bug nghiêm trọng.

.length.to.be.above(0)

String rỗng "" vẫn pass test kiểu dữ liệu! Cần check thêm length > 0.

.to.not.have.property("reason")

Khi login thất bại, Restful-Booker trả {"reason":"Bad credentials"}. Test ngược giúp đảm bảo không có lỗi ẩn!

Code — Kiểm tra response headers: 
// Header có tồn tại?
pm.test("Có header Content-Type", () => {
    pm.response.to.have.header("Content-Type");
});

// Format đúng JSON?
pm.test("Content-Type là JSON", () => {
    pm.expect(
        pm.response.headers.get("Content-Type")
    ).to.include("application/json");
});

// Token đủ dài (bảo mật)?
pm.test("Token có độ dài an toàn", () => {
    const res = pm.response.json();
    pm.expect(res.token.length)
        .to.be.above(10);
});

Tại sao test header?

Nếu server trả text/html thay vì application/json → pm.response.json() sẽ crash → lỗi rất khó debug.

.to.include("application/json")

Dùng include thay vì eql vì header có thể là "application/json; charset=utf-8" — include linh hoạt hơn.

Token length > 10

Token quá ngắn → brute-force dễ dàng = lỗ hổng bảo mật. Đây là security assertion, quan trọng cho tester!

Code — GET /booking/{{booking_id}}: 
const res = pm.response.json();

// So sánh giá trị chính xác
pm.test("Tên khách đúng", () => {
    pm.expect(res.firstname).to.eql("QA");
});

// Kiểm tra boolean
pm.test("Đã đặt cọc", () => {
    pm.expect(res.depositpaid).to.be.true;
});

// Kiểm tra nested object
pm.test("Ngày check-in đúng", () => {
    pm.expect(res.bookingdates.checkin)
        .to.eql("2025-01-01");
});

// Kiểm tra number > 0
pm.test("Giá > 0", () => {
    pm.expect(res.totalprice)
        .to.be.a("number")
        .and.to.be.above(0);
});

.to.eql("QA")

eql = deep equal (so sánh giá trị). Khác equal ở chỗ eql so sánh sâu vào object/array con.

.to.be.true

Kiểm tra boolean chính xác. .to.be.true chỉ pass khi giá trị đúng là true, không pass cho 1 hay "true".

res.bookingdates.checkin

Truy cập nested object: bookingdates là object con chứa checkin và checkout — đi từng tầng.

Golden Rule:

Mỗi pm.test() test MỘT thứ — khi FAIL, biết ngay cái gì hỏng!

Phần 3.1 — Dynamic Variables Của Postman

Dynamic Variables = biến tự sinh giá trị mới mỗi lần gửi request. Cú pháp: {{$tênBiến}} — dùng trực tiếp trong Body, URL, hoặc Headers.

Khi nào dùng?

  • Tạo user/email unique → tránh lỗi "đã tồn tại"
  • Test với dữ liệu ngẫu nhiên → phát hiện edge case
  • Gắn timestamp → theo dõi thứ tự request
  • Chạy Collection Runner nhiều lần → data khác nhau mỗi lần

Lưu ý quan trọng

  • Giá trị thay đổi mỗi lần Send → không dùng để so sánh cố định
  • Muốn giữ lại giá trị → lưu vào Environment trước bằng Pre-request Script
  • Chỉ hoạt động trong Postman, không phải cú pháp JavaScript
Biến Ý nghĩa Ví dụ output
{{$randomInt}}Số ngẫu nhiên 0-1000742
{{$guid}}UUID v4 duy nhấta1b2c3d4-...
{{$timestamp}}Unix timestamp (giây)1722441600
{{$isoTimestamp}}Thời gian ISO 86012025-07-31T...
{{$randomFirstName}}Tên ngẫu nhiênGiang
{{$randomLastName}}Họ ngẫu nhiênNguyen

Phần 3.2 — Dynamic Variables Trong Thực Tế

Dùng trực tiếp trong Body

{
  "email": "user_{{$randomInt}}@test.com",
  "name": "{{$randomFirstName}} {{$randomLastName}}",
  "created_at": "{{$isoTimestamp}}"
}

Mỗi lần Send, Postman tự thay thế các biến này bằng giá trị mới — tránh lỗi "email đã tồn tại" khi test tạo user liên tục.

Kết hợp trong Pre-request Script

// Sinh giá trị động rồi lưu vào Environment
// để tái sử dụng cho nhiều bước trong chuỗi
const uniqueId = pm.variables.replaceIn("{{$randomInt}}");
pm.environment.set("test_run_id", "run_" + uniqueId);

Cách này giúp cả chuỗi request (tạo, sửa, xóa) đều dùng chung một mã định danh duy nhất cho lần chạy hiện tại.

Mẹo: Kết hợp Dynamic Variables với Environment Variables để vừa có dữ liệu mới mỗi lần chạy, vừa giữ được các giá trị dùng chung xuyên suốt chuỗi (như token, base_url).

Phần 4 — Thực Hành Case Study 4

Đề bài

Xây dựng một Collection Postman hoàn chỉnh mô phỏng luồng Booking E2E trên Restful-Booker, gồm 3 request được liên kết (chained) với nhau:

  • Request 1 — Auth: POST /auth → lưu token vào Environment.
  • Request 2 — Tạo Booking: POST /booking → tạo đặt phòng, lưu booking_id.
  • Request 3 — Xem Booking: GET /booking/{{booking_id}} → tra cứu và verify dữ liệu khớp.

Mỗi request phải có ít nhất 2 assertions và chạy PASS 100% khi bấm Collection Runner.

  1. Tạo Environment mới với biến base_url = https://restful-booker.herokuapp.com
  2. Tạo Request 1 (Auth) → POST {{base_url}}/auth với body {"username":"admin","password":"password123"} → Tests Script lưu token
  3. Tạo Request 2 (Create Booking) → POST {{base_url}}/booking → dùng Body có {{$randomInt}} trong totalprice để tạo data unique → Tests Script lưu booking_id
  4. Tạo Request 3 (Get Booking) → GET {{base_url}}/booking/{{booking_id}} → viết assertion verify dữ liệu khớp
  5. Chạy thử từng request theo đúng thứ tự, kiểm tra tab Test Results
  6. Mở Collection Runner → chọn cả 3 request → Run → xác nhận tất cả PASS
// [Request 1 - POST /auth] Tests
pm.test("Auth OK", () => pm.response.to.have.status(200));
const res1 = pm.response.json();
pm.test("Có token trả về", () => pm.expect(res1.token).to.exist);
pm.environment.set("token", res1.token);

// [Request 2 - POST /booking] Tests
pm.test("Tạo booking thành công", () => pm.response.to.have.status(200));
const res2 = pm.response.json();
pm.environment.set("booking_id", res2.bookingid);
pm.test("Booking có id hợp lệ", () => {
    pm.expect(res2.bookingid).to.be.a("number");
});

// [Request 3 - GET /booking/{{booking_id}}] Tests
pm.test("Tra cứu thành công", () => pm.response.to.have.status(200));
const res3 = pm.response.json();
pm.test("Tên khách đúng", () => {
    pm.expect(res3.firstname).to.eql("QA");
    pm.expect(res3.lastname).to.eql("Tester");
});

Phần 4 (tiếp) — Acceptance Criteria & Checklist

Trước khi nộp bài, hãy tự chấm chéo theo checklist sau — đây cũng chính là tiêu chí mình sẽ dùng để đánh giá bài thực hành của bạn:

Cấu trúc Collection — 3 requests được đặt tên rõ ràng, đúng thứ tự (Login → Transfer → Verify).
Environment Variables — đã setup base_url, và các biến trung gian (token, created_user_id) được set qua Tests Script chứ không hardcode tay.
Scripts hoạt động (Chaining) — request sau sử dụng đúng biến được lưu từ request trước, không bị lỗi undefined.
Assertions PASS — mỗi request có tối thiểu 2 assertions và tất cả đều PASS (không có test bị bỏ sót hoặc luôn PASS giả).
Collection Runner chạy xanh 100% — chạy cả 3 requests bằng Runner, kết quả hiển thị toàn bộ PASS, không có lỗi màu đỏ.

Tổng Kết — Kiến Thức Cốt Lõi Buổi 4

Chaining Requests

Output request A → lưu vào Environment Variable → dùng làm Input request B. Đây là nền tảng để xây dựng E2E test tự động.

Assertions Essentials

Bọc mỗi kiểm tra trong pm.test(), dùng pm.expect() để kiểm tra status, body, response time và headers.

Dynamic Variables

{{$randomInt}}, {{$guid}}, {{$timestamp}}... giúp sinh test data unique, tránh trùng lặp mỗi lần chạy request.

Best Practices

Luôn dọn dẹp dữ liệu test (DELETE ở cuối chuỗi), đặt tên biến rõ ràng, và chạy Collection Runner để verify toàn bộ chuỗi tự động.
