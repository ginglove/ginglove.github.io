API Testing là kỹ năng bắt buộc cho mọi Tester muốn tiến xa trong nghề. Đây là lý do:

Shift-Left Testing

Phần 1.0.1b — API Cơ Bản: Toàn Cảnh Trước Khi Thực Chiến

Trước khi mở Postman, hãy nắm chắc 5 trụ cột của bất kỳ API nào. Đây là nền tảng để bạn hiểu mọi thao tác tiếp theo.

1. HTTP Methods — Ngôn Ngữ Giao Tiếp Với Server

GETĐọc dữ liệu — Không gửi Body — Idempotent (gọi 100 lần vẫn giống nhau)
POSTTạo mới — Gửi Body JSON — Không idempotent (mỗi lần tạo 1 bản ghi mới)
PUTThay toàn bộ — Gửi full object — Idempotent — Thiếu field = field bị xoá
PATCHSửa 1 phần — Chỉ gửi field cần sửa — Các field khác giữ nguyên
DELETEXoá — Thường chỉ cần ID trên URL — Response thường 204 No Content
⚠️ Nhầm lẫn #1 của newbie: PUT gửi thiếu field → server hiểu là xoá field đó. PATCH mới chỉ sửa field gửi lên.

2. Status Code — Server Trả Lời Bằng Số

2xx — Thành công:

200 OK (GET/PUT thành công) | 201 Created (POST tạo xong) | 204 No Content (DELETE xong, không trả body)

4xx — Lỗi do Client (bạn sai):

400 Bad Request (body sai format) | 401 Unauthorized (chưa login / token hết hạn) | 403 Forbidden (đã login nhưng không đủ quyền) | 404 Not Found (URL sai hoặc resource không tồn tại) | 422 Unprocessable (data hợp lệ nhưng logic sai)

5xx — Lỗi do Server (họ sai):

500 Internal Error | 502 Bad Gateway | 503 Service Unavailable

⚠️ Nhầm lẫn #2: 401 ≠ 403. 401 = chưa xác thực (chưa login). 403 = đã xác thực nhưng không có quyền.

3. Request & Response — Cấu Trúc Mỗi Lần Giao Tiếp

REQUEST gồm:
① Method: POST
② URL: /api/login
③ Headers: Content-Type
④ Body: {"email":"...","password":"..."}
RESPONSE gồm:
① Status: 200 OK
② Headers: Content-Type
③ Body: {"token":"QpwL5..."}
④ Time: 245ms

4. Authentication — Cơ Chế Xác Thực

Bearer Token — Phổ biến nhất trong REST API:

1. Client gửi POST /login với credentials → nhận token

2. Mọi request sau đính kèm: Authorization: Bearer <token>

3. Token hết hạn → gọi refresh hoặc login lại

JSON (JavaScript Object Notation):

• Key luôn trong "ngoặc kép" — String cũng dùng ngoặc kép (không dùng nháy đơn)

• Number, Boolean (true/false), null: không cần ngoặc

• Truy cập nested: res.data.email — đi từ ngoài vào trong theo tên key

Phần 1.0.2 — Quy Trình API Testing & Postman Trong Từng Bước

API Testing tuân theo quy trình 7 bước chuẩn ISTQB. Postman hỗ trợ trực tiếp ở các bước được đánh dấu :

1
Phân tích yêu cầu API

Đọc API Docs/Swagger, xác định endpoints, methods, request/response schema, business rules.

Postman: Import Swagger/OpenAPI trực tiếp → tự sinh Collection với đầy đủ endpoints, params, examples. Dùng Documentation view để đọc API spec ngay trong Postman.
2
Thiết kế Test Cases

Viết test cases (Happy Path + Negative + Edge Cases) dựa trên BVA, Equivalence Partitioning.

Ngoài Postman: Dùng Excel, TestRail, hoặc Zephyr để quản lý test case. Postman không phải công cụ quản lý test case.
3
Thiết lập môi trường

Cấu hình base URL, credentials, tokens, biến môi trường cho Dev/Staging/UAT.

Postman: Tạo Environment (Dev/Staging/UAT) với Variables. Chuyển đổi môi trường chỉ bằng 1 click dropdown mà không sửa request nào.
4
Thực thi Test

Gửi request, kiểm tra response, chạy assertions tự động, chaining dữ liệu giữa các API.

Postman: Send Request → Tests Script (Assertions) → Pre-request Script (Chaining). Collection Runner chạy toàn bộ suite tự động.
5
Phân tích kết quả

Đọc kết quả PASS/FAIL, kiểm tra response body, status code, headers, response time.

Postman: Test Results tab hiển thị PASS/FAIL từng assertion. Console log (Ctrl+Alt+C) debug chi tiết request/response.
6
Báo cáo Bug

Log bug vào hệ thống quản lý (Jira, Redmine) với evidence: request, response, expected vs actual.

Ngoài Postman: Dùng Jira/Redmine. Tuy nhiên Postman hỗ trợ export request + response làm evidence đính kèm bug report.
7
Regression & CI/CD

Chạy lại bộ test sau mỗi lần fix bug hoặc deploy, tích hợp vào pipeline tự động.

Postman: Newman CLI chạy Collection trong Jenkins/GitLab CI/GitHub Actions. Xuất báo cáo HTML/JUnit tự động sau mỗi build.

Phần 1.0.3 — Thuật Ngữ Cốt Lõi Trong Postman

Trước khi bắt tay vào thực hành, hãy nắm vững 7 khái niệm nền tảng mà bạn sẽ gặp liên tục trong suốt buổi học:

Collection

Thư mục chứa nhóm các requests liên quan. Tương tự Test Suite trong kiểm thử — gom tất cả API của 1 module/feature vào 1 nơi. Có thể chạy toàn bộ bằng Collection Runner.

Request

Một lời gọi HTTP đến server gồm: Method (GET/POST/PUT/DELETE), URL, Headers, và Body (nếu có). Tương tự 1 dòng trong bảng test case — mỗi request = 1 hành động cần kiểm tra.

Response

Kết quả server trả về gồm: Status Code (200, 401, 404...), Headers, Body (thường là JSON), và Response Time. Đây chính là đối tượng mà Tester cần verify (kiểm tra Expected vs Actual).

Environment

Bộ biến (key-value) đại diện cho 1 môi trường cụ thể (Dev/Staging/UAT/Production). Cho phép cùng 1 Collection chạy trên nhiều môi trường chỉ bằng cách đổi Environment — không sửa request.

Variable {{tên_biến}}

Giá trị động được thay thế lúc runtime. Viết trong cặp {{ }}. Dùng để tránh hard-code: {{base_url}}, {{token}}. Biến có 5 cấp ưu tiên: Global → Collection → Environment → Data → Local.

Assertion (Test)

Câu lệnh kiểm tra tự động trong tab Tests: so sánh giá trị thực tế (Actual) với giá trị mong đợi (Expected). Nếu khớp → PASS, nếu sai → FAIL. Viết bằng Chai.js syntax.

Chaining

Kỹ thuật nối các requests lại với nhau: output của request A (VD: token) tự động trở thành input của request B. Đây là nền tảng để xây dựng luồng test End-to-End hoàn chỉnh không cần copy-paste tay.

Phần 1.0.2b — Environments & Variables Trong Postman: Hiểu Sâu Trước Khi Dùng

Environment & Variable là xương sống của mọi bộ test bền vững. Hiểu rõ trước khi bắt tay cấu hình.

Environment Là Gì?

Một bộ biến key-value đại diện cho 1 môi trường cụ thể. Mỗi dự án thực tế có nhiều môi trường:

DEV
base_url = localhost:3000
STAGING
base_url = staging.api.com
UAT
base_url = uat.api.com
PROD
base_url = api.company.com

Lợi ích cốt lõi: Cùng 1 Collection, chỉ đổi Environment → chạy trên môi trường khác mà không sửa bất kỳ request nào.

Variable Là Gì? — Cú Pháp {{tên_biến}}

Giá trị động được thay thế lúc runtime. Viết trong cặp {{ }}. Dùng để tránh hard-code.

// Thay vì hard-code:
❌ https://reqres.in/api/users/2

// Dùng biến:
✅ {{base_url}}/users/{{user_id}}

Tại sao quan trọng?

• Đổi 1 biến → cập nhật tất cả requests cùng lúc
• Không bao giờ quên sửa URL khi đổi môi trường
• Token, user_id tự động truyền giữa các requests (Chaining)

5 Cấp Độ Ưu Tiên Biến (Scope)

Khi cùng tên biến tồn tại ở nhiều cấp, Postman dùng cấp thấp nhất (gần request nhất):

5. GlobalChia sẻ tất cả workspace — ít dùng
4. CollectionGắn vào 1 Collection cụ thể
3. Environment ⭐Phổ biến nhất — bạn sẽ dùng nhiều nhất
2. DataTừ file CSV/JSON khi chạy Runner
1. Local (pm.variables)Chỉ sống trong 1 request — ưu tiên cao nhất

Initial Value vs Current Value

Initial Value Giá trị chia sẻ với team khi Export/Sync. Ai cũng thấy.
Current Value Giá trị chỉ trên máy bạn. Không đồng bộ lên cloud.
Nguyên tắc bảo mật:
• KHÔNG BAO GIỜ đặt password, token, API key vào Initial Value khi làm nhóm
• Dùng Initial Value cho: base_url, username (public data)
• Dùng Current Value cho: password, token, secret key
• Script dùng pm.environment.set() → ghi vào Current Value
Quick Look: Click biểu tượng mắt (Eye icon) góc trên phải để xem nhanh tất cả biến đang active và giá trị hiện tại.

• Kiểm tra nhanh: Mở Eye icon (Quick Look) để xem toàn bộ biến đang active.

Phần 1.1 — Vòng Đời Thực Thi Script Trong Postman

Mỗi request trong Postman luôn tuân thủ nghiêm ngặt 4 giai đoạn. Click vào Pre-request hoặc Tests để xem chi tiết:

Pre-request Script
(Trang bị)
Send Request
(Gửi đi)
Server Response
(Phản hồi)
Tests Script
(Xác minh)
Pre-request = Precondition

Chạy TRƯỚC khi request bay lên Server. Chuyên dùng để:
• Sinh dữ liệu động: timestamp, UUID, hash, random number.
• Gán/cập nhật biến Environment trước lúc gửi request.
• Tính toán giá trị phái sinh: HMAC signature, checksum, encrypted payload.
• Gọi API phụ trợ (pm.sendRequest) để lấy token hoặc seed data.

// VD: Sinh timestamp trước khi gửi
pm.environment.set("timestamp",
  new Date().toISOString());
Tests = Expected Result

Chạy SAU khi đã nhận Response về máy. Chuyên dùng để:
• Parse JSON response: pm.response.json().
• Viết Assertions kiểm tra status code, body, headers, response time.
• Trích xuất dữ liệu (token, ID) lưu vào Environment cho request tiếp theo (Chaining).
• Điều khiển luồng chạy: postman.setNextRequest() để nhảy request.

// VD: Lưu token cho request sau
const res = pm.response.json();

Dùng trực tiếp pm.response mà quên .json() → trả về undefined.

Bẫy #2: So sánh sai kiểu dữ liệu

pm.environment.get() luôn trả về String. So sánh strict với Number sẽ FAIL.

// ✅ ĐÚNG: Ép kiểu trước khi so sánh
pm.expect(res.id).to.equal(
  Number(pm.environment.get("user_id")));

Bẫy #3: Assertion ngoài pm.test()

Viết pm.expect() ngoài pm.test() → lỗi sẽ crash toàn bộ script, không hiện trong Test Results.

// ❌ SAI: Crash script nếu fail

  pm.expect(res.id).to.equal(1);
});

Phần 3 — Viết Assertions: Từ Cơ bản đến Thực chiến

4 Câu hỏi cốt lõi trước khi viết một Assertion

1. Kiểm Tra Cái Gì?

Không chỉ status code! Phải kiểm tra: cấu trúc dữ liệu (có đủ field?), kiểu dữ liệu (id là number?), giá trị (email đúng format?), logic nghiệp vụ (tổng tiền > 0?).

2. Mức Độ Ảnh Hưởng?

Nếu fail → nghiệp vụ có gãy không? VD: sai token → chặn toàn bộ flow = Critical. Sai avatar URL → UI lỗi nhỏ = Minor.

3. Giá Trị Cứng Hay Động?

So sánh .to.equal(2) = cứng (dễ gãy khi data thay đổi). So sánh .to.be.a("number") = mềm (bền hơn). Chọn cứng cho ID/token, mềm cho cấu trúc.

4. Happy vs Negative?

Happy: API trả đúng data khi input đúng. Negative: API trả đúng lỗi khi input sai. Cả 2 đều cần assertion. Negative test PASS = server xử lý lỗi đúng cách.

Status Code Phải Thuộc

2xx — Thành công:

200 OK | 201 Created | 204 No Content

3xx — Redirect:

301 Moved | 302 Found | 304 Not Modified

4xx — Lỗi Client:

400 Bad Request | 401 Unauthorized | 403 Forbidden | 404 Not Found | 422 Unprocessable

5xx — Lỗi Server:

500 Internal Error | 502 Bad Gateway | 503 Service Unavailable

Authentication

Bearer Token — Gửi trong Header:

Authorization: Bearer <token>

Luồng xác thực chuẩn:

1. POST /login → nhận token
2. Đính token vào Header mọi request sau
3. Token hết hạn → gọi refresh hoặc login lại

401 = Token sai/hết hạn  |  403 = Không đủ quyền

JSON & Request/Response

Request gồm: Method + URL + Headers + Body

Response gồm: Status Code + Headers + Body + Time

JSON Rules:

• Key luôn trong "ngoặc kép"
• String dùng "ngoặc kép" (không dùng nháy đơn)
• Number, Boolean, null: không cần ngoặc
• Không trailing comma ở phần tử cuối

JSONPath: res.bank.code — đi từ ngoài vào trong theo tên key
